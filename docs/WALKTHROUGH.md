## 1. The scene, and why it is synthetic

Every image in this repository is generated by `src/feat/scenes.py`. The reason
is not convenience. It is that a failed stitch on two photographs is
*ambiguous*: you cannot tell whether the code is wrong or the photographs were.
When we build the scene ourselves, we know the exact answer.

```python
H_a = cv2.getPerspectiveTransform(quad_a, sensor)  # scene -> photo A
H_b = cv2.getPerspectiveTransform(quad_b, sensor)  # scene -> photo B
img_a = cv2.warpPerspective(scene, H_a, out_size)
img_b = cv2.warpPerspective(scene, H_b, out_size)

H_true = H_a @ np.linalg.inv(H_b)
H_true = H_true / H_true[2, 2]  # pin the scale: H and 5H are the same map
```

Read `H_a @ inv(H_b)` right to left, in the order a point travels: *undo* view B
to land back on the wall, then apply view A's projection. Composing homographies
is matrix multiplication in travel order, and reversing it is a silent bug — the
result is still a homography, just the wrong one.

The final division is not cosmetic. `H` has nine numbers and eight degrees of
freedom, because multiplying all nine by 5 makes `x̃`, `ỹ` and `w̃` all grow by 5
and `x̃/w̃` is unchanged. `H` and `5H` are the same map, so two homographies can
only be compared entry by entry after both are pinned to `H[2,2] == 1`.

Three scenes carry the weight:

- **`textured_wall`** — rectangles, discs and scratches at random sizes and
  colours. Nothing repeats, so every descriptor is distinctive. This is the
  *easy* scene, and it exists mainly to be the control for the next one.
- **`brick_wall`** — a running-bond wall of near-identical bricks. The per-brick
  jitter is a few grey levels on purpose: make it large and each brick becomes
  distinctive, the ambiguity disappears, and the demo built on it quietly stops
  demonstrating anything.
- **`checkerboard`** — because we know the answer. An 8×8 board has
  `(8−1)² = 49` interior X-junctions, and that is what section 3 is scored
  against.

One bug worth recording, because it is the kind that survives review. The first
brick wall used a plausible brick colour of BGR `(58, 74, 148)` on grey mortar
of `96`. It looks like a wall on screen. Its **luminance** is 94.3 against the
mortar's 96 — every detector in this repository works on the grey image, so the
wall was invisible to the thing the scene exists to test, and SIFT found three
keypoints on the whole image. `tests/test_scenes.py` now asserts the contrast in
grey, not in colour:

```python
grey = cv2.cvtColor(scenes.brick_wall(), cv2.COLOR_BGR2GRAY)
dark, bright = np.percentile(grey, [10, 90])
assert bright - dark > 50
assert len(cv2.SIFT_create(800).detect(grey, None)) > 200
```

## 2. What makes a corner a corner

A **feature** is a patch you can find again in another picture of the same
scene. Cut a small square out of a photograph, hand somebody the rest, and ask
them to point at the hole:

- **Flat sky** — hopeless. Slide the patch in any direction and nothing changes.
  Pinned in **zero** directions.
- **A horizon line** — slide it *across* the line and it changes a lot; slide it
  *along* the line and it looks the same. You know you are somewhere on that
  line. Pinned in **one** direction.
- **A window corner** — slide it any way at all and it changes. Pinned in
  **two**, which is exactly what you need to name a single `(x, y)`.

Harris turns "slide the patch and see how much it changes" into arithmetic.
Take a window, shift it by `(u, v)`, and sum the squared differences. A
first-order Taylor expansion — *for tiny steps, a curve looks like a straight
line* — replaces `I(x+u, y+v) − I(x, y)` with `Ix·u + Iy·v`, and the sum collapses
to a quadratic form `[u v] · M · [u v]ᵀ` where

```
        ┌  Σ Ix²     Σ Ix·Iy ┐
   M =  │                     │
        └  Σ Ix·Iy   Σ Iy²   ┘
```

Three windowed sums, and everything about the corner-ness of that patch is in
them. You never actually shift anything. `feat/harris.py`:

```python
def structure_tensor(gray, block=BLOCK, ksize=KSIZE):
    g = gray.astype(np.float32)
    ix = cv2.Sobel(g, cv2.CV_32F, 1, 0, ksize=ksize)
    iy = cv2.Sobel(g, cv2.CV_32F, 0, 1, ksize=ksize)

    def win(a):
        return cv2.boxFilter(a, -1, (block, block), normalize=False)

    return win(ix * ix), win(iy * iy), win(ix * iy)
```

`normalize=False` is load-bearing. A normalised box filter divides by the window
area, turning the *sums* in `M` into *means*. The classification survives that —
the sign of `R` is unchanged — but every absolute number moves by `block²` per
sum and `block⁴` for `R`, and the agreement with `cv2.cornerHarris` that this
module exists to demonstrate would fail.

`M` is symmetric, so it has two real eigenvalues, and they say how steeply the
patch changes along its two principal directions. Both small is flat; one large
is an edge; both large is a corner. Computing two eigenvalues per pixel is two
million small decompositions on a 1080p frame, so Harris uses two identities
that fall out for free — `det(M) = λ₁λ₂` and `tr(M) = λ₁ + λ₂` — and scores

```
R = det(M) − k · tr(M)²
```

`det` is a *product*, so it collapses the moment either eigenvalue is zero: it
rewards *both* being big. `tr²` is the square of a *sum*, so it stays large
whenever *either* is big: it is the penalty.

### The four patches you can do on paper

`examples/01_corner_response.py` prints these, computed with central differences
on 5×5 images of 0s and 10s so the arithmetic fits in your head:

```
patch                  Sxx     Syy     Sxy       det   trace         R      l1      l2  verdict
A flat                   0       0       0         0       0         0       0       0  flat
B vertical edge        150       0       0         0     150      -900     150       0  edge
C corner               100     100      25      9375     200      7775     125      75  corner
D 45-degree edge       125     125    -125         0     250     -2500     250       0  edge
```

**Patch D is the one that matters.** `Σ Ix² = 125` and `Σ Iy² = 125` are *both*
large — read only the diagonal of `M` and this looks exactly like a corner. It
is a 45° edge. The cross term `Σ Ix·Iy = −125` drives `det(M)` to exactly zero,
because the gradient points the same way at every pixel in the window and there
is no second independent direction. **Corner-ness cannot be read off the
diagonal of `M`.**

### The proof against OpenCV

The same script runs the same code on a white square at full Sobel scale, then
brings in the referee:

```
patch              Sxx         Syy         Sxy       det(M)    trace(M)            R
flat                 0           0           0   0.0000e+00           0   0.0000e+00
edge          10404000           0           0   0.0000e+00    10404000  -4.3297e+12
corner         5462100     5462100     1040400   2.8752e+13    10924200   2.3979e+13

OpenCV pre-scales its Sobel by 1/(2^(ksize-1) * blockSize), so R scales by s^4 = 6.250000e-06
largest relative difference vs cv2.cornerHarris : 5.481e-08
Pearson correlation over all 3600 pixels        : 1.0000000000
```

The edge row is hand-checkable: a Sobel-x kernel across a step of 255 gives
1020, and exactly 10 of the 25 pixels in the 5×5 window carry it (two columns,
five rows), so `Σ Ix² = 10 × 1020² = 10,404,000`. That is the number on the
screen, to the digit.

And the scale factor is *derived*, not fitted:

```python
def opencv_response_scale(block=BLOCK, ksize=KSIZE):
    s = 1.0 / ((1 << (ksize - 1)) * block)
    return s ** 4
```

Every entry of `M` is a product of two scaled gradients, so each carries `s²`;
`det` and `tr²` are each a product of two entries, so both carry `s⁴`, and the
whole response scales by `s⁴` and nothing else. `tests/test_harris.py` asserts
the factor comes out of the formula rather than out of dividing the two answers,
because a fitted constant would keep the test passing if OpenCV ever changed its
internal scaling — which is exactly when the claim would have become wrong.

### What `k` decides

`R > 0` requires `λ₁λ₂ > k(λ₁+λ₂)²`. Dividing through by `λ₂²` and writing
`r = λ₁/λ₂` gives `k·r² + (2k−1)·r + k = 0`, whose upper root is the largest
eigenvalue ratio still counted as a corner. At `k = 0.04` that is **23.0**. The
root is real only while `1 − 4k ≥ 0`, which is why:

```
  k = 0.04 -> pixels with R > 0:  108
  k = 0.20 -> pixels with R > 0:   48
  k = 0.24 -> pixels with R > 0:   12
  k = 0.25 -> pixels with R > 0:    0
  k = 0.30 -> pixels with R > 0:    0
```

`k ≥ 0.25` switches the detector off on every image, forever. No error, no
warning, zero corners. If a tutorial tells you to raise `k` until the edges go
away, it can only go so far.

## 3. From a response map to a keypoint list

`R` is a picture. What you want is a list. That takes two more stages — threshold
and non-maximum suppression — and **`cv2.cornerHarris` does neither**. Its
signature is the tell:

```
cornerHarris(src, blockSize, ksize, k[, dst[, borderType]]) -> dst
```

There is no threshold parameter and no suppression radius. Compare the complete
pipeline:

```
goodFeaturesToTrack(image, maxCorners, qualityLevel, minDistance[, ...]) -> corners
```

`maxCorners`, `qualityLevel`, `minDistance` — all three knobs, because that
function *is* the whole algorithm. This is bug shape 1, and the detector is:
**count the algorithm's stages, then count the parameters. A stage with no knob
is a stage you own.**

Now the suppression itself. The version every tutorial ships is:

```python
dilated = cv2.dilate(response, np.ones((ksz, ksz), np.uint8))
mask = (response == dilated) & (response > rel_thresh * response.max())
```

Grey dilation replaces each pixel with the maximum over its neighbourhood, so
`R == dilate(R)` is *meant* to mean "this pixel is the largest in its
neighbourhood". It actually means "this pixel is **equal to** the largest in its
neighbourhood", and when several adjacent pixels share the exact same maximum —
a **plateau** — every one of them passes. On the checkerboard, whose answer we
know:

```
  true interior corners              49
  pixels above 1% of R.max           2484
  naive R == dilate(R), all          814
  naive R == dilate(R), interior     784
  component-wise NMS, all            79
  component-wise NMS, interior       49
  naive NMS on the BLURRED board     226
```

784 against 49 — sixteen times too many, in tight clumps. The fix is to label
the surviving mask and keep one point per connected component:

```python
n_labels, labels = cv2.connectedComponents(mask, connectivity=8)
for label in range(1, n_labels):
    ys, xs = np.nonzero(labels == label)
    best = int(np.argmax(response[ys, xs]))
    peaks.append((int(xs[best]), int(ys[best])))
```

The point kept is the component's own argmax, not its centroid: a centroid on an
L-shaped plateau can land on a pixel that is not in the component at all.

**The last row of that table is the important one.** Blur the checkerboard by a
single 3×3 kernel and the naive version drops from 814 to 226, because the blur
breaks the exact ties. Sensor noise does the same. So the bug reproduces on your
clean synthetic test image and *not* on your real photographs, which makes it
look like the test is wrong. That is the shape of the whole class.

## 4. Why corners are not enough

Harris is rotation invariant for free — eigenvalues do not care which way the
coordinate frame points. It is not scale invariant, and the reason is in the
signature: `blockSize` is a fixed number of pixels.

`examples/02_scale_breaks_harris.py` measures repeatability — the fraction of
full-resolution keypoints re-detected within 3 px after the second image is
scaled down, with the scaled points mapped back by dividing by the factor:

```
  scale        size  Harris n   repeat   SIFT n   repeat
   1.00  (800, 600)       520   100.0%      601   100.0%
   0.80  (640, 480)       422    76.7%      600    80.7%
   0.65  (520, 390)       366    61.0%      600    70.2%
   0.50  (400, 300)       326    35.4%      600    57.6%
   0.40  (320, 240)       284    15.0%      600    41.9%
   0.30  (240, 180)       198     5.0%      600    28.3%
   0.25  (200, 150)       149     2.7%      523    22.8%
```

Two honest readings. Harris collapses — 2.7% at quarter scale, which is a
matcher that works beautifully on two photographs taken from the same distance
and falls apart the moment one camera is closer. And **SIFT also falls**, to
22.8%. Scale invariance is a large improvement, not a magic property; anyone who
tells you SIFT is scale invariant *full stop* has not measured it.

The threshold matters to this experiment. Both detectors are cut at a fraction of
*that image's own* maximum, never an absolute number:

```python
return harris.peaks_component_nms(harris.harris_response(gray.astype(np.float32)), rel)
```

`R` is fourth order in the gradient — `det` and `tr²` are both products of two
gradient-squared sums — so halving an image's contrast divides `R` by sixteen. An
absolute cut-off would confound the experiment completely and the "scale failure"
would be mostly a thresholding artefact. (`tests/test_harris.py` asserts the
fourth-order behaviour directly.) This is exactly the reasoning behind
`goodFeaturesToTrack`'s `qualityLevel`.

The second half of the example isolates the mechanism. One disc, one contrast,
only its size changing, response read at the disc's centre:

```
 blockSize   largest radius still detected
         5                               4
        15                              11
        31                              22
```

A small disc sits entirely inside the summation window, so the window sees
structure in two directions and `R` is huge. Grow it past the window and the
window sees nothing but flat interior, so `R` goes to **exactly zero**. There is
no gradual decline and no threshold that rescues it: the feature does not weaken,
it ceases to exist. And the cut-off tracks the window and nothing else — which is
why `blockSize` is not a sensitivity knob. It is a declaration of what size of
structure this detector can see, and a detector can only make one.

The only way out is to stop looking at the image once.

## 5. Scale space, and where to stop building

A **scale space** is the image blurred with a ladder of increasing σ. Blurring
simulates stepping back from a poster: fine print disappears first, big shapes
survive. Subtracting neighbouring blur levels gives the **difference of
Gaussians**, and what survives the subtraction is the detail that lived
*between* those two levels.

```python
sigmas = [sigma0 * (2.0 ** (i / n_intervals)) for i in range(n_intervals + 3)]
blurred = [cv2.GaussianBlur(g, (0, 0), s) for s in sigmas]
```

Geometric, not arithmetic: the visual difference between σ = 1 and 2 is the same
as between 4 and 8, and an arithmetic ladder would sample the coarse end far too
finely and the fine end not at all.

The `+ 3` is the bookkeeping everyone gets wrong once. N blurred images give N−1
DoG layers, and the extremum test needs a layer above and below the one being
searched, so N−3 are searchable. Ask for 3 usable layers and you must build 6.
`examples/03_scale_space.py` prints it, and `tests/test_scalespace.py` asserts it
for several N:

```
 octave  downsample         image    sigmas  DoG layers  searchable  extrema
      0           1    (800, 600)         6           5           3      403
      1           2    (400, 300)         6           5           3      138
      2           4    (200, 150)         6           5           3       58
      3           8     (100, 75)         6           5           3       15
```

A keypoint is a pixel that beats all 26 of its neighbours — 8 in its own layer,
9 above, 9 below — done with three dilations and a max rather than a Python loop
over 26 offsets:

```python
max27 = np.maximum(np.maximum(dilated[i - 1], dilated[i]), dilated[i + 1])
min27 = np.minimum(np.minimum(eroded[i - 1], eroded[i]), eroded[i + 1])
mask = ((cur == max27) | (cur == min27)) & strong
```

Both maxima and minima, because the subtraction order is a convention: with
`next − current`, a bright blob on a dark background gives a *negative* response.
Search only for maxima and you find half the keypoints and never notice.

The scale at which a point wins that contest **is** its characteristic size, and
that is where scale invariance comes from — not from a trick applied afterwards,
but from the way the point was found in the first place. The bottom-left panel of
figure 03 draws each keypoint as a circle of its own σ, which is that sentence as
a picture.

### What was built and what was called

This is SIFT stage 1. Stages 2 to 4 — sub-pixel quadratic refinement,
low-contrast and edge rejection, orientation assignment, the 128-D descriptor —
are `cv2.SIFT`. That split is a decision (`DECISIONS.md` §3), and the example
**measures what is on the other side of the line** rather than asserting it was
fine:

```
  scale  DoG (ours)     SIFT      ORB   Harris
   1.00   100.0%   100.0%   100.0%   100.0%
   0.80    60.7%    80.7%    95.3%    76.7%
   0.65    43.5%    70.2%    91.2%    61.0%
   0.50    31.4%    57.6%    70.0%    35.4%
   0.40    18.2%    41.9%    52.3%    15.0%
   0.30    10.6%    28.3%    33.0%     5.0%
```

Read the two ends of the Harris and DoG columns against each other. At a mild
0.8× our bare extrema are **worse** than Harris — no sub-pixel refinement, so a
point that genuinely was re-detected often lands more than 3 px from where it
should. At 0.3× they are twice as good, because by then Harris is not finding the
structure at all. **The pyramid buys large scale changes; it does not buy
accuracy.** The gap between our column and SIFT's is exactly what stages 2 to 4
are worth, and it is not small.

One methodological note that is itself a lesson. The contrast floor is set so
the bare extremum test returns about 600 keypoints — the same budget the SIFT and
ORB calls are given:

```python
CONTRAST = 10.0
```

Repeatability has the candidate count in its denominator, so comparing 2200
unfiltered candidates against 600 filtered keypoints would make our detector lose
for a reason that has nothing to do with scale. Match the budget, then compare.

## 6. Descriptors: SIFT and ORB

A detector says *where*. A descriptor says *what the patch looks like*, as a
fixed-length vector you compare with arithmetic. The same physical corner
photographed twice produces different pixels — different scale, rotation and
lighting — so the descriptor's design goal is to produce nearly the same numbers
anyway.

**SIFT** is 128 float32 values: a 16×16 window rotated to the keypoint's dominant
orientation, split into a 4×4 grid of cells, each cell an 8-bin histogram of
gradient orientations. Normalise to unit length (that is the illumination
invariance — double every gradient and the unit vector is bit-for-bit
identical), clip every entry at 0.2, renormalise.

The layout is worth being able to index rather than only describe. Cell
`(row r, col c)`, bin `b` sits at `(r*4 + c)*8 + b`, and
`examples/04_descriptors.py` checks both directions:

```
SIFT layout: cell (row 2, col 3), bin 5 is entry ((2*4 + 3)*8 + 5) = 93
  flat des[93]              = 9.0000
  reshaped des.reshape(4,4,8)[2,3,5] = 9.0000
  and backwards: 93 // 8 = 11 (cell), 93 % 8 = 5 (bin); cell 11 is row 2, col 3
  L2 norm of this descriptor  = 512.70
```

That last line is a trap with a long tail. OpenCV normalises to unit length and
then **multiplies by 512 and rounds**, so `np.linalg.norm(des[i])` is about 512
and the dtype is float32 holding whole numbers. Feed these straight into
something that expects unit vectors — a cosine layer, a distance threshold quoted
from a paper — and every number is 512× too big.

**ORB** is 256 bits: 256 "is pixel P brighter than pixel Q?" tests on a fixed
pattern, rotated by the keypoint's intensity-centroid angle. 32 bytes, exactly
16× smaller, and the distance between two of them is XOR and popcount:

```
ORB Hamming, first two descriptors: XOR then popcount = 123, cv2.norm(NORM_HAMMING) = 123, agree = True
  first byte: 145 = 10010001
              171 = 10101011
         XOR: 58 = 00111010  -> 4 differing bits in this byte alone
```

Two anchors worth memorising: a descriptor against itself scores 0, and two
unrelated descriptors sit near 128 — half the bits differ, which is what random
coin flips do. Measured here, the mean bits set across ORB's descriptors is
**132.4**, which is what a well-balanced binary code looks like.

### The cost, measured

```
matching cost on this CPU (minimum of 5 runs, knnMatch k=2)
  SIFT    800 x   800 descriptors ->    2.74 ms      4.28 ns per pair
  ORB     800 x   800 descriptors ->    1.04 ms      1.63 ns per pair
  ORB is 2.6x cheaper per descriptor pair here, on 32 bytes against 512.
```

Two design choices in that harness are the difference between a measurement and
a number:

```python
best = min(best, time.perf_counter() - t0)
...
return best, best / pairs * 1e9
```

The **minimum** over repeats, not the mean, because a timing sample is a true
cost plus interference and interference is strictly positive — it can only make a
run slower. And divided by `len(a) * len(b)`, so two detectors that found
different numbers of keypoints are still comparable; raw wall-clock on different
descriptor counts measures the detectors, not the metrics.

2.6×, not the 16× the byte counts might suggest. Both matchers are memory-bound
at this size and OpenCV's L2 path is well vectorised. And the number moves:
across seven repeated runs on this laptop the ratio ranged from **2.0× to 3.1×**,
which is what a wall-clock measurement on a machine doing other things looks
like. The honest claim is "a small single-digit factor on this CPU at this
descriptor count", and quoting a single decimal place as though it were a
property of the algorithms would be a worse answer than quoting the range.

### Invariance, with a control

```
 degrees      SIFT       ORB   raw 16x16 patch
       0    100.0%    100.0%            100.0%
      10     96.9%     96.8%             93.8%
      20     96.9%     97.4%             70.3%
      30     96.2%     96.1%             44.4%
      45     95.6%     94.7%             19.0%
      60     96.2%     94.4%             17.2%
      90     98.8%     93.7%             18.8%
```

The third column is the point. A raw 16×16 pixel patch has a location and a scale
and no orientation handling at all, and it collapses from 100% to 19%. Without
that column, "SIFT is rotation invariant" is an assertion; with it, the
experiment demonstrably *could* have come out the other way. That is the test bug
shape 4 demands of every demo.

## 7. Matching, and why raw matching lies

Matching answers one question, once per descriptor: *which descriptor in the
other image is the same physical point?* Nearest-neighbour search always returns
an answer and never returns "I do not know". On a brick wall that guarantee is
the whole problem.

The brute-force matcher is nine lines, and the whole of it is one identity:

```python
d2 = (a * a).sum(1)[:, None] - 2.0 * (a @ b.T) + (b * b).sum(1)[None, :]
np.maximum(d2, 0.0, out=d2)
idx = np.argpartition(d2, kth=min(k, d2.shape[1] - 1), axis=1)[:, :k]
```

`||a − b||² = a·a − 2a·b + b·b`, so every pairwise distance comes out of a single
matrix multiply and no `N × M × 128` intermediate is ever built. Written the
obvious way — `((A[:, None, :] - B[None, :, :]) ** 2).sum(-1)` — 500×500 SIFT
descriptors would allocate 128 MB and 5000×5000 would allocate 12 GB. The
identity is not a micro-optimisation; it is the difference between running and
not running. The clamp before the square root is there because cancellation can
leave a squared distance at −1e-9, and `sqrt` of that is a NaN that sorts
unpredictably. `argpartition` rather than `argsort` because we want the k
smallest, not an ordering of all M.

It agrees with OpenCV:

```
brute force, written out in numpy, against cv2.BFMatcher (300 x 300 SIFT descriptors)
  identical nearest neighbour on : 100.0% of queries
  largest distance disagreement  : 1.520e-05
```

The Hamming version agrees *exactly* on distances, because they are integer bit
counts and there is no floating-point excuse available. Its indices sometimes
differ, and only ever where two train descriptors are tied at the same distance —
integer distances make exact ties common, and `argpartition` breaks them by
memory order while OpenCV breaks them by scan order. `tests/test_matching.py`
asserts the distances exactly and checks that every index disagreement is a tie,
because asserting index equality would be asserting an implementation detail of
a tie-break.

### The brick wall

```
--- repeated brick wall (the scene that lies) ---
keypoints: query 650, train 678, of which 207 query points have a true partner

  raw nearest neighbour        kept  650  correct   19  precision   2.9%  recall   9.2%
  cross-check alone            kept  101  correct    8  precision   7.9%  recall   3.9%
  ratio test @ 0.75            kept   20  correct    5  precision  25.0%  recall   2.4%
  ratio 0.75 + cross-check     kept   11  correct    2  precision  18.2%  recall   1.0%
```

Against the same pipeline on the distinctive scene:

```
--- distinctive clutter (the easy scene) ---
  raw nearest neighbour        kept  801  correct  296  precision  37.0%  recall  90.5%
  cross-check alone            kept  391  correct  280  precision  71.6%  recall  85.6%
  ratio test @ 0.75            kept  292  correct  273  precision  93.5%  recall  83.5%
  ratio 0.75 + cross-check     kept  276  correct  263  precision  95.3%  recall  80.4%
```

**Lowe's ratio test** keeps a match only when the nearest neighbour is clearly
nearer than the runner-up:

```python
return [pair[0] for pair in knn_pairs
        if len(pair) == 2 and pair[0].distance < ratio * pair[1].distance]
```

Three details in that one line, each a real bug avoided. It is written
**multiplied, not divided**: with ORB the distances are small integers and `d2`
can legitimately be 0 when two descriptors are bit-identical, so `d1/d2 < r`
raises `ZeroDivisionError` on exactly the input the test exists to reject — and
the multiplied form does the right thing at `d2 == 0`, keeping nothing, because a
perfect tie is maximal ambiguity. `pair[0]` is the *nearer* neighbour, since
`knnMatch` returns each pair sorted nearest-first; invert them and the test
becomes `d2 < 0.75·d1`, which is essentially never true, and the symptom is zero
matches on two images that obviously overlap. And the `len(pair) == 2` guard is
for the case where the *train* set holds fewer than two descriptors — a near-blank
second image — which has nothing to do with where a keypoint sits in the query
image.

Note what the test does **not** measure. It is not a check that `d1` is small. A
match with a tiny absolute distance is discarded if the runner-up is equally
close. It measures **separation**, not quality.

**Cross-check** asks a different question — *does the other image agree?* — and
kills a different disease:

```python
back = cv2.BFMatcher(...).match(des_train, des_query)
home = {m.queryIdx: m.trainIdx for m in back}
return [m for m in matches if home.get(m.trainIdx, -1) == m.queryIdx]
```

`cv2.BFMatcher(..., crossCheck=True)` does this too, but it cannot be combined
with `knnMatch(k=2)` — OpenCV asserts `K == 1 && update == 0` — so with the flag
you get the ratio test or cross-check, never both. That is a limitation of the
*flag*, not of the idea: matching backwards with `k=1` and keeping the round
trips takes four lines and composes with anything. The ratio test allows
many-to-one and cannot see it; cross-check forbids many-to-one by construction
and cannot see ambiguity. Combined on the clutter scene they reach 95.3%
precision, the best row in the table.

### The number nobody prints

A working matcher reporting an ambiguous scene looks identical, from outside, to
a broken matcher. The number that separates them is the *absolute* `d1`:

```
  clutter  median d1 =  259.1   median d1/d2 = 0.901
  bricks   median d1 =   57.5   median d1/d2 = 0.963
```

On the brick wall the matches are **excellent** — median distance 57.5 against
the clutter's 259.1 — and entirely ambiguous. The descriptors are not failing.
They are matching beautifully, to the wrong brick. That is a scene problem, and
loosening the ratio to 0.9 does not resolve the ambiguity, it admits it.

## 8. The five shapes of bug

The heart of the repository. `src/feat/bugs.py` reproduces each shape
deliberately and returns the measurements; `examples/06_five_shapes_of_bug.py`
draws them; `tests/test_bugs.py` asserts that each still misbehaves in the
documented direction — because a demonstration of a bug rots faster than any
other code, and the prose around it goes on claiming otherwise.

Every report carries four fields, and the last two are the transferable half:

```python
@dataclass(frozen=True)
class BugReport:
    number: int
    shape: str
    instance: str
    detector: str   # the ten-second check
    symptom: str    # how to recognise it from a bug report, with no source in front of you
    numbers: dict
```

**Shape 1 — the partial implementation.** Covered in section 3 above: 49 true
corners, 784 from the naive suppression, 49 from the fixed one, and 226 once the
board is blurred. *Detector:* count the stages, then count the knobs.

**Shape 2 — the hidden operator in the name.** `BFMatcher(normType, crossCheck)`
has three morphemes and every one changes the answer. The detector says: split
the name into morphemes, then design an input that makes each one fire.

| morpheme | the input that fires it | what happens |
|---|---|---|
| `crossCheck` | `knnMatch(k=2)` | raises `K == 1 && update == 0` — **loud** |
| `crossCheck` | `match()` with and without | 1200 matches becomes 422, same method name, no sign a filter ran — **quiet** |
| `norm` | `NORM_HAMMING` on float32 | raises `batchDistance` type assertion — **loud** |
| `norm` | `NORM_L2` on ORB's uint8 | runs, silently, and is worse — **quiet** |
| `BF` | twice the descriptors | 3.3× the time: the cost is `O(N·M)` |

The quiet metric case is the dangerous one, and the numbers say why:

```
  norm, quiet: right metric   HAMMING (right) raw NN   kept 1200  correct  323  precision  26.9%  recall  80.3%
  norm, quiet: wrong metric   L2      (wrong) raw NN   kept 1200  correct  244  precision  20.3%  recall  60.7%
  norm, quiet: right + ratio  HAMMING (right) +ratio   kept  221  correct  200  precision  90.5%  recall  49.8%
  norm, quiet: wrong + ratio  L2      (wrong) +ratio   kept  102  correct   88  precision  86.3%  recall  21.9%
```

Raw nearest neighbour keeps one match per query under either metric, so the two
are compared at an identical kept count and only the correct count can move: 323
to 244. After a ratio test the **precision** most people print barely moves
(90.5% → 86.3%) while the **recall** most people do not print falls by more than
half. *Symptom:* a pipeline that "sort of works" and gets worse on hard pairs.

**Shape 3 — the ambiguous unit.** `DMatch.distance` is a Hamming bit count in
0–256 for ORB and an unbounded L2 float for SIFT:

```
  orb: d1 min / median / max         11.0 / 55.0 / 87.0
  sift: d1 min / median / max        35.0 / 267.9 / 423.2
  fixed cut d1 < 50 keeps (orb)      36.7%
  fixed cut d1 < 50 keeps (sift)     1.5%
  ratio test 0.75 keeps (orb)        18.4%
  ratio test 0.75 keeps (sift)       36.8%
  spread, fixed cut (x)              24.44
  spread, ratio test (x)             2
```

One line of code, `if m.distance < 50`, carried between two pipelines, changes
meaning by a factor of **24**. The same threshold written as a *ratio* has a
spread of **2**, because dividing cancels the unit. That is the fix, and it
generalises: **a dimensionless threshold is the only kind that travels.**
`tests/test_matching.py` asserts it directly — multiply every descriptor by 7 and
the ratio test keeps exactly the same matches, while a fixed cut loses more than
four fifths of them.

Two more units in the same neighbourhood, measured in the same report:
`KeyPoint.size` is a **diameter** (crop with it as a radius and every patch is
twice the intended size), and `KeyPoint.angle` is in **degrees**, and is −1 when
the detector assigned no orientation.

**Shape 4 — the demo with no control.** The advertised result, on the
distinctive scene: the ratio test takes precision from 37.0% to 93.5% while
keeping 83.5% recall. True, and unfalsifiable as presented — there is no input in
that demo that could have printed the opposite. Two controls are added:

```
  [distinctive clutter] raw nearest neighbour kept 801  correct 296  P 37.0%  R 90.5%
  [distinctive clutter] ratio test 0.75 kept 292  correct 273  P 93.5%  R 83.5%
  [repeated brick wall] raw nearest neighbour kept 650  correct 19  P 2.9%  R 9.2%
  [repeated brick wall] ratio test 0.75 kept 20  correct 5  P 25.0%  R 2.4%
  correct matches lost, clutter      23
  correct matches lost, bricks       14
```

On the control scene precision still improves — the ratio test is not broken —
and the number of *correct* matches falls from 19 to 5. That is the filter
working exactly as designed and producing a match set too small to fit a
homography with. The second control is the scoring metric itself: score shape 2's
metric bug by precision alone and it looks nearly fine; score it by recall and it
has lost half its correct matches. **A demo is only as honest as the number it
chooses to report, and precision alone can always be bought by keeping less.**

**Shape 5 — the fact with an expiry date.** Every line is a question put to this
interpreter rather than to the internet, and every answer is version-stamped:

```
  cv2.__version__                    4.14.0
  opencv-python installed            5.0.0.93
  opencv-contrib-python installed    4.14.0.94
  hasattr(cv2, 'SIFT_create')        True
  hasattr(cv2, 'xfeatures2d')        True
  SURF binding present               True

```

Four facts from nine lines. SIFT is at the `cv2` top level, so it came from main

two lines are False *on this build*: `LightGlueMatcher` and `ALIKED` ship in
OpenCV 5's base wheel. Whichever answer they print, the answer has a version
attached to it, which is the entire habit the shape is teaching.

## 9. RANSAC and the DLT

### Why least squares dies

Least squares minimises the sum of *squared* errors, which assumes every
measurement is a mildly noisy inlier. A 0.5 px error contributes 0.25 to the sum;
a 200 px error contributes 40,000. One wrong match outvotes 160,000 good ones.
It is the arithmetic of a mean salary in a room where somebody walked a
billionaire in.

Measured on 30 correspondences from a known `H` with 12 (40%) replaced by junk:

```
  least squares on all 30    : worst corner error   1807.413 px
  RANSAC (ours)              : worst corner error      1.020 px   inliers 18/30
  cv2.RANSAC                 : worst corner error      2.181 px   inliers 18/30
  cv2.USAC_MAGSAC            : worst corner error      1.024 px   inliers 18/30
```

A factor of **1772**. Not a little worse — it is not an estimate of anything.
Note also what is *not* being measured: the residual on the fitted points. A model
can fit its own data beautifully and still push the image corners a thousand
pixels out of place, because the residual is what the fit minimised.

### The DLT

Start from `x' = x̃/w̃` and multiply through by `w̃` to clear the fraction. What is
left is **linear** in the nine entries of `H`, and each correspondence
contributes two rows:

```
[ -x  -y  -1   0   0   0   u*x   u*y   u ]
[  0   0   0  -x  -y  -1   v*x   v*y   v ]
```

Stack them and the system is `A·h = 0`, which has no useful solution as stated —
`h = 0` always works and any scaling of a solution is also a solution. So fix the
scale and ask a different question: which *unit-length* `h` makes `‖A·h‖`
smallest? The SVD answers exactly that, and the answer is the direction `A`
shrinks most:

```python
_, _, vt = np.linalg.svd(rows)
h_norm = vt[-1].reshape(3, 3)
h = np.linalg.inv(t_dst) @ h_norm @ t_src
return h / h[2, 2]
```

`Vt[-1]` rather than "the column matching the smallest singular value" is
deliberate: with exactly four correspondences `A` is 8×9, so NumPy returns eight
singular values for nine directions in h-space, and the ninth is the exact null
space that never had a singular value to be smallest. `Vt[-1]` is right either
way.

It agrees with OpenCV's own least-squares solve to floating-point noise:

```
  largest entry-wise difference from cv2.findHomography(..., 0) : 4.086e-14
  the four source points pushed through our H land within        : 1.421e-14 px of the targets
```

**Hartley normalisation is not optional**, and this is the single most common
reason a hand-rolled homography "almost works":

```python
mu = p.mean(axis=0)
mean_dist = np.sqrt(((p - mu) ** 2).sum(axis=1)).mean()
scale = np.sqrt(2.0) / mean_dist if mean_dist > 1e-12 else 1.0
```

Centroid to the origin, mean distance √2, solve, un-normalise. Skip it and the
columns of `A` span five orders of magnitude — `u·x` runs to 1e5 while its
neighbour is 1 — and the SVD spends its precision on the large columns. The
symptom is an `H` that fits its four sample points and visibly misfits everything
else, with no error raised. `tests/test_ransac.py` measures both versions on
points around x = 4000 and asserts the un-normalised residual is at least 100×
worse.

### The threshold

A reprojection residual is the distance between two 2-D points, so **both**
coordinates are noisy, and `r²/σ²` follows chi-squared with **2** degrees of
freedom. The 95% point of χ²(2) is 5.99, so `t = sqrt(5.99)·σ ≈ 2.45σ`.

The widely quoted 1.96 is the two-sided 95% interval for a *single* scalar —
χ²(1), whose 95% point is 3.84 and `sqrt(3.84) = 1.96`. It is the right answer to
a different question: a point-to-**line** residual, such as the epipolar distance
in `findFundamentalMat`. Knowing which case you are in is the actual skill.

Derived rather than tabulated, so there is no SciPy dependency for two numbers:

```python
if dof == 2:
    return float(np.sqrt(-2.0 * np.log(1.0 - confidence)) * sigma)
```

For two independent Gaussians the probability the distance stays under `t·σ` is
`1 − exp(−t²/2)`; set that to 0.95 and rearrange to get `t² = −2·ln(0.05) =
5.9915`. The sweep measures what getting it wrong costs, on the same data:

```
  t (px)  what it is                      kept    true  outliers   corner err
    0.98  1.96*sigma  (1 DoF, wrong)        14   14/18         0     0.571 px
    1.22  2.45*sigma  (2 DoF, 95%)          18   18/18         0     1.020 px
    1.52  3.03*sigma  (2 DoF, 99%)          18   18/18         0     1.020 px
    3.00  3.0 px      (a magic number)      18   18/18         0     1.020 px
   60.00  60.0 px     (far too loose)       19   18/18         1    11.291 px
```

Two failure directions, both real. Row 1: the 1-DoF threshold discards four
genuine inliers. Its corner error happens to look fine — fourteen well-spread
points still pin a homography — and the real damage is that the measured inlier
ratio drops from 18/30 to 14/30, which sits in the *exponent* of the iteration
formula below and inflates the cost super-linearly. Row 5: one admitted outlier
moves the worst corner by 11.3 px against 1.02. That is the whole argument for
RANSAC, in one row.

### The iteration count

One sample is all-inliers with probability `wˢ`, so `N` independent samples are
all contaminated with probability `(1 − wˢ)ᴺ`. Require that below `1 − p` and
solve:

```
N = ceil( log(1 - p) / log(1 - w^s) )
```

```
  w = 0.5, sample size s = 1..8 : [7, 17, 35, 72, 146, 293, 588, 1177]
  s = 4 (homography), w sweep   : [(0.8, 9), (0.6, 34), (0.5, 72), (0.3, 567), (0.2, 2876)]
```

The **ceiling** is not cosmetic: the line case (`s = 2`) lands on 16.008, and at
exactly 16 trials the success probability is 0.98998, fractionally under the 0.99
requested. `tests/test_ransac.py` asserts that inequality directly.

The sample size sits in the *exponent*, so each extra point roughly doubles the
work at `w = 0.5` — 72 iterations for a 4-point homography against 17 for a
2-point line. That is why you always fit with the smallest sample the model
allows. And the `w` sweep is why hard-coding an iteration count fails silently:
at 20% inliers the formula asks for 2876, so a hard-coded 100 returns a
confidently wrong model with no warning at all.

`ransac_homography` therefore recomputes the budget as it goes:

```python
if best is None or mask.sum() > best_mask.sum():
    best_mask, best_h = mask, h
    if adaptive and 0 < mask.mean() < 1:
        need = iterations_needed(mask.mean(), sample=4, success=success)
        budget = min(max_iterations, max(drawn, need))
```

On the example-07 fixture that converges in 95 samples where 2000 was budgeted.

### The step people skip

```python
for _ in range(5):
    refit = dlt_homography(src[best_mask], dst[best_mask])
    ...
    new_mask = residuals(refit, src, dst) < threshold
    if np.array_equal(new_mask, best_mask):
        break
```

The model out of the loop was fitted to exactly four points and carries all four
points' noise at full strength. Refitting on the whole consensus set is safe —
the outliers are already gone — and it is the difference between a homography
correct in kind and one correct in pixels. Skip it and a stitched panorama gains
a soft double edge you will spend an afternoon blaming on the blender.

It is iterated to a fixed point rather than done once, because a better model
admits inliers the four-point model just missed, and those inliers make the next
model better again. That is the cheap half of LO-RANSAC; on this fixture it is
worth about one recovered inlier and a factor of two in corner accuracy.

One more guard, and it earns its line:

```python
if not np.all(np.isfinite(h)):
    continue
```

Three of four sampled points can be collinear, or two can coincide; then `A`
loses rank and `H` comes back `inf` or `nan`. Without the guard the NaN
propagates into the best model and every later comparison is `False`, so the run
"succeeds" and returns garbage.

## 10. Warping and compositing

Estimating `H` and painting pixels are two different steps, and they fail
differently. `examples/08_panorama.py` runs the whole chapter on a pair with two
deliberate defects: an intruder object pasted at two irreconcilable positions,
and a 22% exposure difference.

```
keypoints   base 2503   other 2795
ratio-test survivors: 717
RANSAC threshold 2.448 px (2 DoF, 95%, sigma = 1.0 px), 6 samples drawn
inliers: 620 / 717      outliers: 97   inlier ratio 86.5%
max corner error vs the known H:  ours 0.435 px   cv2.findHomography 0.277 px  (620 inliers)
matches on the intruder: 7, rejected by RANSAC: 7
```

Read the third and fourth lines together. **97 of the 717 matches that survived
the ratio test are geometrically impossible.** The ratio test is not a filter for
correctness; it is a filter for ambiguity. And all seven matches on the intruder
are rejected — *all* of them, because the object is bright and unique, so SIFT
describes it crisply and the ratio test waves every one through. They really are
unambiguous. They are also all wrong. Only geometry can tell you that a
confident, unambiguous match is impossible.

### The canvas

```python
allc = np.vstack([corners_base, warped]).reshape(-1, 2)
x_min, y_min = np.floor(allc.min(axis=0)).astype(int)
x_max, y_max = np.ceil(allc.max(axis=0)).astype(int)
t = np.array([[1.0, 0.0, -x_min], [0.0, 1.0, -y_min], [0.0, 0.0, 1.0]])
```

Transform the four corners of the source, take the bounding box together with the
base image's own corners, prepend the translation that moves the minimum to
(0, 0). The tutorial default `(w_base + w_other, max(h_base, h_other))` happens
to survive a left-to-right pivot and nothing else:

```
canvas sized from the transformed corners: 1085 x 558, shifted by (0, 31)
naive canvas   1280 x 480  keeps  506342 image pixels
correct canvas 1085 x 558  keeps  527726 image pixels   (+21384 against the naive crop)
```

31 rows above the top of the frame, 21,384 image pixels silently cropped, and
190 columns of black padding on the right that were never needed. The cropping is
the dangerous half, because a panorama with a straight-cut corner reads as a
deliberate crop rather than a bug.

Both images are warped, not just one — the base by the pure translation `T`, the
other by `T @ H` — so that the two sides of the seam are resampled identically
and the agreement measured below is not contaminated by an interpolation
difference. And the coverage masks come from warping a field of 255s, not from
`pixel > 0`, because a dark region of a real image contains legitimate zeros and
`pixel > 0` would punch holes in the mask exactly where the scene is dark.

### Health, in two separate numbers

```
                           overlap px      NCC  mean|diff|  >40 apart  largest blob
  clean, our H                 129544   0.9992        1.19      0.00%            10
  clean, known H_true          129534   0.9993        1.13      0.00%             9
  + exposure difference        129544   0.9963       29.34     16.54%          6539
  + the intruder too           129544   0.8342       36.03     23.02%         10067
```

A ladder, because "the overlap disagrees" has three causes with three different
fixes and a single quality score cannot tell them apart. Each rung adds exactly
one defect to the same pair and the same homography, so whatever moves is caused
by the thing just added.

- **Rows 1 and 2** — our homography agrees with the true one to four decimal
  places in NCC. The estimator is not the problem in any row below, and that is
  established before anything else is looked at.
- **Row 3** — mean `|diff|` jumps by a factor of 25 while NCC moves in the third
  decimal. NCC is invariant to a uniform gain and mean `|diff|` is not, so
  reading the two together separates *misaligned* from *differently exposed* —
  and only the second is fixed in the compositor.
- **Row 4** — NCC finally falls, and the largest disagreeing blob grows to
  roughly the intruder's own area. A disagreement that is **blob-shaped** means
  something moved; one that is a thin **halo** along every edge in the frame
  means the homography is wrong.

### The seam

```
seam at x = 639, measured as the largest column-to-column brightness jump:
  hard paste  :  29.91 grey levels
  feathered   :   6.77 grey levels   (4.4x smaller)
```

The hard paste is `out[base_mask] = base[base_mask]` — an honest two-line
compositor whose failure is a **step**, because one column comes entirely from
one exposure and the next entirely from the other. Feathering weights each image
by its distance to its own nearest invalid pixel:

```python
w_base = cv2.distanceTransform(canvas.base_mask.astype(np.uint8), cv2.DIST_L2, 3)
w_other = cv2.distanceTransform(canvas.other_mask.astype(np.uint8), cv2.DIST_L2, 3)
total = np.maximum(w_base + w_other, 1e-6)
w_base, w_other = w_base / total, w_other / total
```

Each image's contribution is 1 deep inside it and 0 at its border, so the two
weights cross over smoothly somewhere in the overlap. Two details are the
difference between working and not: the weights are normalised by their **sum**,
not clamped independently — independent weights do not add to 1 in the overlap,
so the blend darkens there, a soft band instead of a hard step and harder to
notice — and the sum is floored before the division, because outside both masks
it is zero and `0/0` is a NaN that survives the cast to uint8 as an arbitrary
byte value.

**What feathering does not fix.** Where the two images genuinely disagree it
paints half of each, so the intruder appears twice at half strength. Feathering
hides an exposure step; it cannot hide a contradiction. The production answers
are a seam routed around the disagreement (`cv2.detail_GraphCutSeamFinder`, which
is what `cv2.Stitcher` uses internally) or a per-pixel median over three or more
frames, which votes out anything not in the same place in a majority of them.
Neither is implemented here, and the README says so under limitations rather than
letting the picture imply otherwise.
